# Store試作収集の本体UI接続に向けた設計判断

この文書は、Mac App Store版の試作収集（`Store*Collector` 群）を本体UIへ接続できるかを判断するための設計記録です。安全条件の正本は [入力経路の調査](APP_STORE_SOURCE_AUDIT.md) であり、この文書はその条件を置き換えません。ここに書く案はいずれも未実装・未実証であり、実署名Sandboxでの動作、Appleの審査適合性を示すものではありません。接続可否の最終判断は、後述の実証手順を終えた結果に基づいて別途行います。

現状、本体側の収集入口（`AIMeterApp.swift` の `runLocalCollectorScript()`）はStoreビルドでは `StoreCollectionUnavailable.notConnected` を返し、試作収集はUI・保存・Widgetのいずれにも接続されていません。この文書は、その状態を変える前に必要な設計と実証を整理します。

## 監査が挙げた未実証点の整理

監査の「実施前の確認」から、接続の判断に直接関わるものを抜き出します。

### 対象の同一性

- `StoreScopedDirectory` は `lstat` と `fstat` の間の最終要素の置換を拒否する試作であり、最初の `lstat` より前に選択先や祖先が置き換わる場合、bookmarkの選択対象と実際に開いたFDの同一性を証明しません。scope内でFDを保持しFD相対で読むだけでは、この最初の結び付けを検証したことになりません。
- 独立レビューでは、選択ディレクトリ配下の固定中間パスを検査した後、その親がシンボリックリンクに差し替わると、URLベースの走査が選択範囲外へ及び得ることも判明しています。`StoreSafeFileTree` と各コレクタはFD相対の走査でこの競合に強い側ですが、起点となるroot FDの取得自体が上記の結び付けに依存します。
- bookmarkの解決成功、scopeの開始、パスとinodeの一致だけでは、選択時の原本との同一性を証明しません。inodeの再利用、同一inodeの内容変更、移動、再起動、再マウント、異なるファイルシステムは条件が異なります。

### 状態の区別

- Store用の試作収集入口は、空・誤選択・解析不能と正しい集計0を識別できません。入力ごとの判定を実装・検証するまで、返った数値を成功結果として表示・保存しません。
- 既存実装には、入力が存在しない場合に空の結果を返す箇所があり、許可不足、データなし、一部経路のみ取得できた場合を区別できるかは未検証です。
- 取得できない連携をゼロや未検出と誤表示しないことを、本体とWidgetの双方で確認する必要があります。

### 推定値・参考値

コレクタ内部の結果型は区別を持ち始めていますが、いずれも利用者向け表示には未接続で、実データ互換性は未検証です。

| コレクタ | 返すもの | 推定・参考の性質 |
| --- | --- | --- |
| Codex（`collectStoreCodex`） | `StoreCodexOutcome`（未検出／無効データ／枠のみ／部分／完全） | 累積値の減少やキャッシュ増分の不整合がある行以降は集計せず部分結果とする。利用枠のみで使用量がない場合は結果型で区別する。枠の一部が省略されたイベントの解釈は正式仕様未確認。 |
| Gemini（`StoreGeminiCollector`） | 入力元ごとの状態と `brainUsesEstimate` | トークン情報がないbrainログで本文の文字数から使用量を推定する。chatsの `total` とinput/outputの関係は実データ仕様が未確認。 |
| Claude（`StoreClaudeCollector`） | ログ・設定・projectsの状態を分離 | `projects` 由来は期間不明の参考値として返し、週・月のログ集計へ混ぜない。必要な値が不完全な場合は参考値を返さない。 |
| Copilot（`StoreCopilotCollector`） | メッセージ件数と時刻付き累積checkpointを分離 | 累積値を期間内の確定使用量として扱わない。同一時刻の値が矛盾する場合は部分取得または不確定とする。 |
| Grok Bot（`StoreGrokCollector`） | 週次quotaと文字数からの推定を分離 | quotaの鮮度は未確認（`Freshness.unverified`）。複数replicaの重複可能性を結果に含める。 |
| Cursor（`StoreCursorCollector`） | JSONの内容を読まず、更新日時に基づくファイル件数 | 確定使用量や現在の残量ではない代理指標。 |
| Windsurf | 試作コレクタなし | 現行DBとWALは別々にコピーされるため、ペアの一貫性は保証されない。整合したsnapshotの取得方法が未実証。 |

## 同一性検証の具体案

### 選択時に記録するもの

現行の `StoreBookmarkStore.save()` はbookmarkデータだけを保存し、選択対象の同一性は記録していません。選択の直後、アクセス権が有効な間に次を合わせて保存します。

- bookmarkデータ（現行どおり。再選択なしにアクセスを再開するためのもの）
- 解決URLの `URLResourceValues` から得る file resource identifier（`fileResourceIdentifierKey`）と volume identifier（`volumeIdentifierKey`）。file resource identifierはボリューム内でファイル実体を指し、同一ボリューム内の名前変更や移動では変わらないため、パス文字列より強い同一性の手掛かりになります
- 選択対象を開いたFDの `fstat`（`st_dev`、`st_ino`、種別）。file resource identifierが取得できない環境での補助、および取得可否自体の記録に使います
- 選択種別（ディレクトリかファイルか）と入力元ID。現行は `claude.settings` のようなファイル選択もあり、同一性の扱いを分ける必要があります

ネットワークボリュームなど、file resource identifierが得られない、または安定しない環境では同一性を記録できたことにせず、その入力元はStore版では未対応として扱います（後述の合格基準で確認します）。

### アクセス時に照合するもの

収集のたびに、scope開始後に次の順で照合します。いずれか一つでも一致しなければ、その入力元は収集せず「要再選択」とします。パス文字列の一致は同一性の根拠にしません。

1. bookmarkを解決し、scopeを開始する（現行どおり）
2. 解決URLの file resource identifier と volume identifier を再取得し、選択時の記録と照合する。これにより、祖先がシンボリックリンクに差し替わって別の実体を指す場合は識別子が変わり、検出できます
3. パスからroot FDを開き（現行の `O_NOFOLLOW` 等を維持）、FDに対して属性取得（`fgetattrlist` 等）を行い、FDが指す実体のファイルIDを、選択時に記録した識別子・`st_dev`/`st_ino` と照合する。検証対象を「開いた実体そのもの」にすることで、lstatとopenの間の競合だけでなく、最初のlstatより前の置換もこの段階で検出できます
4. FDからパスを逆引きできる場合は、解決URLと突き合わせて移動を検出します。同一ボリューム内の移動は同一性を保ちますが、選択範囲の前提が変わるため、初版では移動も再選択として扱う案を採ります
5. 照合がすべて通ったFDを起点に、現行どおりFD相対で走査・読取を行います。走査中の個別エントリの競合対策は `StoreSafeFileTree` と各コレクタの既存実装（fstatatとopenatの照合、読取前後のメタデータ比較）を維持します

### StoreScopedDirectoryの不足と最小の変更

現行実装の不足は次の4点です。

- 選択時の同一性の記録がなく、照合の基準が「その場でlstatした値」しかない。基準自体が置換後の対象を指していれば検出できません
- 照合が `st_dev`/`st_ino` のみで、inodeの再利用に弱い
- ディレクトリ専用であり、ファイル選択（`claude.settings`）の同一性は扱っていない。Claudeコレクタは補助設定FDについて読取前後の `stat` 比較を自前で行っていますが、選択時との結び付けはありません
- 失効・移動・照合失敗を、呼び出し側の状態（要再選択）へ一貫して伝える経路が未接続です

最小の変更は次の形です。新規の基盤は作らず、既存の `Operations` 注入パターンを保ちます。

- `StoreBookmarkStore` に同一性レコード（file resource identifier、volume identifier、`st_dev`、`st_ino`、選択種別）をbookmarkと対で保存する拡張を加える。旧データ（同一性レコードなし）は「同一性未記録」として要再選択に倒し、暗黙に信頼しません
- `StoreScopedDirectory.withRoot` に期待する同一性レコードを渡し、open直後のFD照合（上記3）を追加する。失敗は既存の `Failure.changed` として返し、状態側で要再選択へ変換します
- ファイル選択用に、同じ照合を行う単一ファイル版の入口を用意し、Claudeの補助設定FD取得をそこへ寄せます
- 合成テストでは `Operations` の差し替えで「lstat前に祖先が置換された」ケースを決定的に再現し、現行実装では検出できず、照合追加後は `.changed` になることを確認します

残る限界も明記します。同一ユーザーの敵対的プロセスが選択と同時に置換し、かつ識別子まで一致させる攻撃は、この照合でも完全には証明できません。本検証の目的は、誤選択・移動・失効・通常の競合を確実に検出し、範囲外のデータを成功結果として読まないことです。

## 状態の区別

### 現状

- 状態管理の試作 `StoreSourceState` は、結果を成功（件数）／未検出／対象不適切／失敗の4値で受けます。正しく完了した走査の0件は成功（0件）として未検出と区別でき、その点は単体テスト（`testZeroIsDistinctFromMissingAndInvalid`）で担保されています
- 一方で、コレクタ内部の細かい状態（推定を含むか、部分である理由、参考値のみか）は `StoreSourceState` の結果型を運べず、UIへ渡す変換が存在しません。許可の状態（未選択／許可済み／要再選択／解除済み）と収集の状態の分離は `docs/APP_STORE_DESIGN.md` の設計どおりですが、実装上の対応付けは未接続です

### 提案する表示状態

コレクタ結果から表示状態への変換（アダプタ）を入力元ごとに定義し、UIとWidgetは共通の表示状態だけを見ます。

| 表示状態 | 意味 | 数値の扱い |
| --- | --- | --- |
| 未選択 | 入力元が選ばれていない | 表示しない |
| 未取得 | 許可はあるが、この許可状態ではまだ収集していない | 表示しない |
| 取得中 | 収集の途中 | 表示しない（以前の成功は古い値と明示する場合のみ） |
| 実測（完全） | 同一性を検証し、走査と解析が完走した | 確定値として表示する。該当0件なら0 |
| 実測（部分） | 一部の入力・レコードが欠けたまま集計できた | 部分であることと、欠けた対象を明示して表示する |
| 推定を含む | 実測と推定が混ざる、または推定のみ | 「目安」と明示し、確定値と合算しない |
| 参考値のみ | 期間不明などの理由で確定集計に入れられない値 | 本体の期間別表示とは別の参考枠で、性質を明示して表示する |
| データなし | 同一性を検証し走査は完走したが、対象データが存在しない | 0とは表示せず、データが見つからない旨を示す |
| 解析不能 | 対象は開けたが内容を解釈できない | 数値を表示せず、対象の確認を案内する |
| 対象違いの疑い | 同一性照合の失敗、構造が想定と異なる | 数値を表示せず、再選択を案内する |
| 要再選択 | bookmarkの失効・移動・権限喪失 | 数値を表示せず、再選択を案内する |
| 失敗 | 上記以外の取得失敗 | 再試行を示す。以前の結果は最終成功時刻を添える |

「真の0」は、同一性が検証でき、走査が完走し、対象形式のレコードが0件だった場合に限ります。フォルダが空、ファイルが空、形式に合う行がない、対象構造が見つからない場合は、それぞれデータなし・解析不能・対象違いの疑いに倒し、0にしません。

### 推定値・参考値を返すコレクタの扱い

Store初版では次を提案します。いずれも、実データ仕様の確認が取れたものから再評価します。

- 対象外とするもの：Cursorのファイル件数（使用量の代理指標であり、利用量として表示する根拠がない）、Grok Botのtranscript文字数推定、Gemini brainの文字数推定分。これらは初版では収集対象から外し、サービス自体または該当入力元を「未対応」と表示します。Geminiはトークン情報を持つレコードのみを実測とし、推定が必要なレコードは解析不能側の件数として扱う案も併記しますが、実データで推定レコードの割合が大きい場合はbrain入力元ごと対象外とします
- 参考値として別枠表示を検討するもの：Claudeの `projects` 合計（期間不明を明示）、Copilotのcheckpoint（累積値で期間の開始が不明であることを明示）。本体の期間別数値には混ぜません
- 鮮度未確認の明示付きでも初版では見送るもの：Grok Botの週次quota。鮮度の根拠が取れるまで残量として表示しません
- Windsurfは試作コレクタ自体がなく、DB/WALの整合したsnapshot取得が未実証のため、初版の対象外とします

## 実証手順

接続前に、実署名Sandboxで合成フィクスチャだけを使い、次の順で確認します。実ログ、実API資格情報、実サービスとの接続は使いません。既存の未実行ハーネス `Tests/StoreSandboxQA`（bookmarkの保存・復元と、置換3種を選択・scope開始・lstat・openの各時点で試す手順）は、同一性照合の観測に使える既存資産として位置づけます。

### フィクスチャ

- 既知の値を持つログ構造のコピー：期待する集計値が事前に計算できる合成ログ（サービスごと、期間境界を含む）
- 空の対象：空フォルダ、0バイトのファイル、形式に合うレコードが1件もないファイル
- 壊れた対象：途中に壊れた行・欠けた必須項目・矛盾する累積値を含むファイル
- 無関係なフォルダ：同名のファイルを含むが形式が異なるもの、想定構造を持たないもの
- 置換ケース：選択後に最終要素・親・ディレクトリ自体を別の合成フォルダやリンクへ置き換えたもの（ハーネスの `replace-root`／`replace-parent`／`replace-directory`）
- Windsurf用：DB単体、DBとWALの組（対象外の判断材料として記録のみ）

### 手順と合格基準

1. 単体テストで、同一性照合の失敗・祖先置換・inode再利用を模したケースがすべて収集開始前に拒否されること。成功扱いの数値が一切返らないこと
2. ハーネスで、選択→終了→再起動→復元の通常系が通り、置換ケースの全時点（scope開始後、lstat前後、open後）で範囲外の合成マーカーを読まないこと。`OUTSIDE_MARKER_OBSERVED` が出た時点で不合格として止めます
3. 置換・移動・失効の各ケースで、本体の表示が要再選択または対象違いの疑いになり、数値が表示・保存されないこと
4. フィクスチャの各対象で、表示状態が期待どおりに分かれること。特に、既知値フィクスチャは期待値と一致する実測になり、空フォルダはデータなし、壊れた対象は解析不能または部分、無関係なフォルダは対象違いの疑いまたは未検出になり、いずれも0と表示されないこと。真の0は「形式に合うレコードはあるが期間内の対象が0件」のフィクスチャでのみ確認します
5. 推定・参考に分類した値が、確定値の表示場所に現れないこと。対象外とした入力元が未対応と表示されること
6. 部分許可（複数入力元のうち一部だけ許可）で、欠けた入力元が明示され、残りの結果が部分として表示されること。サービス全体が未許可のとき数値が出ないこと
7. 取得できない連携が、本体とWidgetの双方でゼロや未検出と誤表示されないこと
8. 検証できた条件と未検証の条件（macOSの版、署名の種類、ファイルシステム、Widget実機など）を分けて記録すること

小さく分け、各段で単体テストを先に通します。実署名Sandboxでの確認は段の途中ではなく、縦切りが通った後にまとめて行います。

| 段 | 内容 | 主なリスク |
| --- | --- | --- |
| PR-1 | 同一性レコードの保存と読み戻し（`StoreBookmarkStore` 拡張）。旧データは要再選択に倒す。単体テストのみ | 保存形式の移行ミスで既存の選択を壊す。実データ移行はStore版未配布のため影響は試作内に閉じます |
| PR-2 | `StoreScopedDirectory` への同一性照合追加と、ファイル選択用の入口。祖先置換を再現する合成テスト | 照合が厳しすぎて通常の移動・名前変更まで失敗にする、または緩すぎて検出できない。合格基準2の観測で調整します |
| PR-3 | コレクタ結果から表示状態へのアダプタと、`StoreSourceState` の結果型の拡張。推定・参考・対象外の分類をここで固定 | 状態の取り違えが誤表示に直結します。フィクスチャ期待値との対応表をテストに含めます |

## 判断材料の要約

### 接続してよい条件

- 同一性照合（PR-1、PR-2）が入り、単体テストとハーネスの置換ケースで範囲外を読まないことが確認できている
- 表示状態のアダプタ（PR-3）が入り、空・解析不能・誤選択と真の0が画面上で区別され、推定値が確定値として表示されない
- 縦切り（PR-4）と実証手順の合格基準1〜8を、接続するサービスについて満たしている
- 対象外とした入力元・サービスが、未対応として明示される

### まだ止める条件

- 同一性照合なしに、現行の `StoreScopedDirectory` だけでroot FDの結び付けを済ませようとする場合
- 置換ケースで範囲外のマーカーやデータを一度でも読んだ場合
- 空・解析不能・誤選択のいずれかを0や未検出と表示してしまう経路が残る場合
- 推定値・参考値・代理指標を、確定した使用量や残量として表示・保存する場合
- 実データ仕様が未確認のコレクタを、合成フィクスチャの結果だけで本番接続する場合
- Windsurfのように、整合した入力取得の方法自体が未実証の入力元

この文書の案に沿って実装と実証が進むまでは、Store試作収集は本体UIへ接続せず、`StoreBuildGuard` の `#error` も解除しません。
